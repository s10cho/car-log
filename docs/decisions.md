# 기술 결정 기록

Foundation(Slice 0) 단계에서 확정한 사항과 그 이유. 뒤집을 때는 이 문서를 함께 고친다.

## 확정

### 최소 OS: iOS 15.0 / Android API 26

핸드오프 문서의 정책은 "최신 안정 OS 중심, 유지보수 부담이 큰 구형 OS는 적극 제외"다.

- **iOS 15.0** — Flutter 3.47 / Xcode 26의 기본값이자 하한. 더 올려도 얻는 API가 없고,
  플러그인 호환 문제만 늘어난다.
- **Android 26 (8.0)** — Flutter 기본값 24에서 올렸다. 26부터 Notification Channel과
  Adaptive Icon 을 그대로 쓸 수 있다.

  > `java.time` 도 26부터 쓸 수 있지만, `flutter_local_notifications` 가 core library
  > desugaring 을 요구해서 결국 켜야 했다(`isCoreLibraryDesugaringEnabled`). release
  > 빌드에서만 걸리는 검사라 debug 빌드만 돌리던 CI 가 놓쳤고, 그래서 CI 의 Android
  > 잡을 release 빌드로 바꿨다.

### 환경 분리는 `--dart-define`, 네이티브 flavor 없음

DEV / PRODUCTION 두 가지만 둔다. Android product flavor + iOS scheme 을 만들면
Xcode scheme, xcconfig, CI 매트릭스가 전부 두 배가 되는데, 지금 얻는 것은 앱을 두 개
동시에 설치하는 편의뿐이다.

대신 `AppConfig` 가 환경별 값을 들고 있고, DEV와 PRODUCTION은 **다른 로컬 DB 파일**을
쓴다. 개발 중 데이터가 실사용 데이터를 오염시키지 않는다.

동시 설치가 실제로 필요해지면 그때 flavor를 도입한다.

### 상태관리: Riverpod, 코드 생성 없음

`flutter_riverpod` 의 provider를 직접 선언한다. `riverpod_generator` / `riverpod_lint` 는
쓰지 않는다.

이유: `riverpod_lint` → `custom_lint` 가 `analyzer` 8.x 를 고정하는 바람에 drift, riverpod,
build_runner 가 모두 몇 버전씩 뒤로 묶였다. 명시적으로 선언한 provider는 생성 코드가 없어
읽기도 쉽다. build_runner는 Drift 하나만 쓴다.

### DB: Drift

Vehicle ↔ Maintenance ↔ MaintenanceType ↔ Reminder 는 관계형 모델이 자연스럽고,
Reactive Query와 Migration이 둘 다 필요하다.

`AppPreferences` 키/값 테이블 하나로 시작한다. 도메인 테이블은 Slice 1에서 추가한다.

### 자격증명은 Drift에 넣지 않는다

AI API Key, OAuth Access/Refresh Token은 `SecureStore`(Keychain / Keystore)에만 둔다.
Drift에도, 일반 preferences에도, export 백업에도 들어가지 않는다.

### 번들 ID: `com.s10cho.carlog`

`flutter create` 기본값은 iOS `com.s10cho.carLog`, Android `com.s10cho.car_log` 로 서로
달랐다. iOS 번들 ID에는 밑줄을 쓸 수 없으므로 양쪽을 소문자 한 단어로 통일했다.

### 기본 정비 항목의 주기는 일반 권장값이다

`lib/core/database/built_in_maintenance_types.dart` 에 10개 항목을 심는다. 이 중 스펙이
수치를 명시한 것은 엔진오일(10,000 km 또는 12개월)과 와이퍼(12개월) 둘뿐이고, 나머지
8개는 국내 승용차에서 통용되는 범위를 골랐다. 제조사 수치가 아니다.

지어낸 값을 진실처럼 보이게 두지 않기 위해 두 가지를 한다. 항목 관리 화면에 "일반적인
권장값"이라고 적고, 앱 전체 기본값과 차량별 override를 모두 수정 가능하게 둔다.

시드는 `code` 로 중복을 판단하는 `insertOrIgnore` 라서, 사용자가 고친 이름이나 주기를
앱 업데이트가 되돌리지 않는다.

### 홈은 기록이 있는 항목만 보여준다

기본 항목 10개를 전부 나열하면 새 차량의 홈이 "기록 없음" 아홉 줄에 묻힌다. 홈은 이
차량에서 실제로 기록한 항목만 급한 순(지남 → 임박 → 여유)으로 보여주고, 전체 목록은
항목 관리 화면에서 본다.

### 기본 항목은 삭제할 수 없다

이름과 주기는 고칠 수 있지만 삭제는 사용자 정의 항목만 가능하다. 정비 기록이 항목을
참조하므로 삭제는 이력을 함께 날리거나 실패한다. 참조가 있는 사용자 정의 항목도
삭제를 막고 기록이 몇 건인지 알려 준다.

### 알림은 날짜 기준 항목만 예약한다

앱이 닫혀 있는 동안 주행거리가 얼마나 늘었는지 알 방법이 없다. 그래서 "10,000 km 마다"
같은 거리 기준 항목은 예약할 달력 시점이 없고, 앱을 열었을 때 홈에서 상태로만 보여준다.
기간 기준이 있는 항목만 알림을 만든다. 알림 설정 화면에 이 사정을 적어 둔다.

### 알림 권한은 사용자가 알림을 켤 때 요청한다

첫 실행에 권한 창을 띄우지 않는다. 기본값이 "꺼짐"이고, 설정에서 켜는 순간 요청한다.
거절하면 스위치를 되돌리고 기기 설정에서 허용해야 한다고 알린다. 맥락 없이 뜬 권한 창은
대개 거절당하고, iOS는 한 번 거절하면 다시 물을 수 없다.

### Android 알림은 inexact 알람을 쓴다

`AndroidScheduleMode.inexactAllowWhileIdle`. 정비 알림은 초 단위로 정확할 필요가 없는데,
exact 알람은 Android 12+ 에서 사용자가 직접 켜 줘야 하는 별도 권한을 요구한다. 몇 분의
오차와 권한 요청 하나를 맞바꾼다.

### 예약은 매번 전부 지우고 다시 건다

변경이 생길 때마다 DB에서 계획 전체를 다시 계산하고 `cancelAll()` 후 새로 예약한다.
diff를 계산하면 알림 id를 안정적으로 유지해야 하고 그 매핑이 또 상태가 된다. 항목 수가
수십 개 수준이라 전부 다시 거는 비용이 무시할 만하다.

규칙은 `planReminders()` 라는 순수 함수에 있고, 플랫폼 호출은 그 계획을 적용하기만 한다.
덕분에 알림 로직을 플러그인 없이 테스트한다.

### 영수증은 상대 경로로 저장한다

`ReceiptAssets.relativePath` 에는 `receipts/<uuid>.jpg` 처럼 문서 디렉터리 기준 상대
경로만 넣고, 읽을 때 현재 문서 디렉터리에 붙여 푼다. iOS 는 앱을 다시 설치하면 컨테이너
UUID 가 바뀌므로 오늘 저장한 절대 경로가 내일 아무 데도 가리키지 않을 수 있다.

### 영수증 파일은 차량 삭제 시 손으로 지운다

DB 는 차량 → 기록을 cascade 로 지우지만 파일 시스템은 따라오지 않는다. 차량을 지우기
전에 그 차량 기록에 붙은 영수증 경로를 모아 두었다가 함께 지운다. 그러지 않으면 문서
디렉터리에 영원히 남아 사용자 저장 공간과 백업 용량을 차지한다.

### 이미지가 아닌 영수증은 미리 보지 않는다

PDF 영수증도 저장은 하지만 앱에 문서 렌더러가 없어 미리 보기는 제공하지 않는다. 파일
이름과 함께 "미리 볼 수 없습니다"라고 알린다. 보여줄 수 없는 것을 보여주는 척하는 것보다
낫고, 필요해지면 뷰어와 함께 도입한다.

### 업로드 서명 키는 저장소 안에 git-crypt 로 둔다

`android/upload-keystore.jks` 와 `android/key.properties` 를 암호화해서 커밋한다.
`flutter create` 가 넣어 둔 `android/.gitignore` 의 `key.properties` / `**/*.jks` 줄은
지웠다 — ignore 되면 추적 자체가 안 된다.

이유: 서명 키를 잃으면 같은 앱을 업데이트할 수 없다. 저장소에 암호화해서 두면 백업이
자동으로 따라오고, 기기를 바꿔도 clone + `git-crypt unlock` 이면 끝난다. 별도로 챙겨야
하는 파일이 하나 줄어든다.

비밀번호는 생성 시 무작위로 만들어 `key.properties` 안에만 있다. 즉 **git-crypt 키가
모든 것을 여는 하나의 비밀**이 된다. 그 키를 잃으면 서명 키도 함께 잃는다.

키가 없는 클론(잠금 해제 전, CI 의 PR 빌드)에서는 Gradle 이 debug 키로 서명해 빌드는
통과시킨다. 그래야 외부 기여자나 잠금 없는 CI 에서도 컴파일 검증이 돌아간다.

### AI 결과는 항상 Draft 다

Provider 가 읽어 온 값은 폼의 입력칸을 채울 뿐, 곧바로 저장되지 않는다. AI 가 채운
칸에는 "AI 가 채운 값입니다. 확인해 주세요."를 붙여, 틀린 값이 조용히 기록되지 않게 한다.

항목 이름은 특히 조심한다. Provider 는 이름(문자열)으로 답하고, 그 이름이 카탈로그에
정확히 있을 때만 선택한다. 없는 이름은 버린다 — 모델이 지어낸 항목을 만들지 않는다.

기록에 "AI 가 만든 것"이라는 표시는 남기지 않았다. 사용자가 확인하고 고친 뒤 저장한
값이므로 결국 사용자의 데이터이고, 출처 표시를 남기려면 필드 단위로 원본과 수정본을
모두 보관해야 하는데 그 복잡도에 값하는 쓰임이 아직 없다. 필요해지면 그때 넣는다.

### AI 전송 동의는 한 번, 맥락과 함께 받는다

영수증에는 정비소·날짜·금액이 담긴다. 첫 분석 직전에 어느 Provider 로 무엇이 가는지
말하고 동의를 받는다. 거절하면 아무것도 보내지 않고 수동 입력으로 남는다.

### AI 실패는 언제나 수동 입력으로 떨어진다

타임아웃, 네트워크 없음, 키 거부, 모델이 산문으로 답한 경우까지 — 모두 메시지를 띄우고
폼을 그대로 둔다. 분석은 편의일 뿐이고, 실패가 기록을 막아서는 안 된다.

재시도는 한 번뿐이다. 일시적 실패(429, 5xx)만 다시 보내고, 거부된 키는 다시 보내도
거부된다. 무한 재시도는 사용자의 데이터와 Provider 할당량을 태운다.

오류 메시지에 응답 본문을 넣지 않는다. 본문이 영수증 내용을 되인용할 수 있다.

### 백업은 사람이 읽을 수 있는 JSON 파일 하나

내보내기는 들여쓴 JSON 파일을 만들고, 시스템 공유 시트로 넘긴다. iCloud Drive,
Google Drive, 메일, 어디로든 사용자가 고른다.

Drive 나 iCloud 를 각각 SDK 로 붙이지 않았다. 목적지마다 OAuth 와 계정 연결이 붙는데,
공유 시트 하나면 같은 일을 하고 이 앱이 인증할 대상도 없다. "사용자가 자기 데이터를
소유한다"는 원칙에도 이쪽이 맞는다 — 파일을 열어 읽을 수 있다.

### 백업 포맷은 Drift 행 JSON 이 아니라 직접 쓴다

`backup_mapping.dart` 에 필드 이름을 손으로 적었다. 백업은 테이블이 바뀐 미래의 앱에서도
읽혀야 하는데, 생성된 이름을 쓰면 스키마와 함께 흔들린다. `format_version` 을 두고, 더
새로운 형식은 읽지 않고 거부한다.

### 백업에 영수증 사진은 넣지 않는다

사진까지 담으면 파일이 수백 배로 불어나 옮기기 어려운 백업이 된다. 아무도 가져가지 않는
백업은 백업이 아니다. 기록의 나머지 필드는 그대로 살아남고 첨부만 빠진다 — 복원된 기록이
존재할 수 없는 파일을 가리키지 않도록 `receiptAssetId` 도 내보내지 않는다.

### 복원은 병합이 아니라 교체다

반쯤 적용된 복원은 두 기기의 데이터가 섞인 상태를 남기고, 어느 쪽이 맞는지 알 방법이
없다. 트랜잭션 안에서 전부 지우고 전부 넣는다. 되돌릴 수 없으므로 확인 창에서 백업 날짜와
담긴 양을 보여주고 무엇이 사라지는지 말한다.

AI Provider 선택과 전송 동의는 백업에서 뺐다. 키는 보안 저장소에 있어 따라오지 않는데,
선택만 복원하면 연결된 것처럼 보이면서 동작하지 않는다.

### 3D 차량은 flutter_scene + Kenney Car Kit

`flutter_scene` 0.23 으로 Flutter GPU 위에서 직접 렌더한다. WebView 기반
(`model_viewer_plus`)은 화면마다 웹뷰를 띄우고 네트워크나 번들 에셋 경로가 얽혀서
이 정도 장식에 비싸다.

모델은 **Kenney Car Kit (CC0)** 10종. 저작자 표시조차 필요 없고 개당 180KB 남짓이라
전부 넣어도 2MB 다.

**실제 브랜드 모델(테슬라·현대 등)은 쓰지 않는다.** 자동차 형상과 로고는 상표이고,
스토어에 올리는 앱에 남의 상표를 넣는 것은 별개의 문제다. 대신 차체 형태(세단·SUV·밴·
트럭…)를 고르게 해서 사용자가 "내 차"로 알아볼 수 있게 했다.

플랫폼 설정이 필요하다 — iOS `FLTEnableFlutterGPU`, Android
`io.flutter.embedding.android.EnableFlutterGPU`. 켜지 않으면 로드가 예외로 떨어진다.

`flutter_scene:init` 의 DataAsset 파이프라인은 Flutter master 채널이 필요하므로 쓰지
않고, 런타임에 `Node.fromGlbBytes` 로 읽는다.

Kenney 의 GLB 는 텍스처를 `Textures/colormap.png` 로 **참조만** 하므로 그대로 열면
전부 흰색으로 나온다. `tool/embed_glb_textures.py` 로 텍스처를 파일 안에 넣었다.

### 3D 는 실패해도 화면을 막지 않는다

Flutter GPU 를 못 쓰는 기기, 모델 로드 실패, 위젯 테스트 환경에서는 `CarSilhouette`
(직접 그린 차 그림)로 떨어진다. 차는 장식이고, 장식 때문에 화면을 못 쓰게 되면 안 된다.

`Node` 는 캐시하지 않고 **바이트만** 캐시한다. Node 는 자신이 추가된 Scene 에 속하므로
같은 인스턴스를 두 Scene 에 넣으면 한쪽이 빈 화면이 된다 — 실제로 위저드에서 본 차가
홈에서 사라졌다.

### 차량 등록은 한 번에 하나씩 묻는다

폼 하나에 모든 칸을 늘어놓으면 사용자가 답하기 전에 계획을 세워야 한다. 차 등록에는
자연스러운 순서(무엇인지 → 뭐라 부를지 → 얼마나 달렸는지)가 있어서 그 순서대로 묻고,
답한 것은 칩으로 남겨 사라지지 않게 한다.

선택 항목은 마지막 단계에 모아 두고 비워 둔 채 끝낼 수 있다.

### 관리 점수와 배지

정비 항목 목록은 "내 차가 괜찮은가"를 사용자가 직접 계산하게 만든다. 0–100 점수 하나가
그 계산을 대신하고, 올릴 여지도 준다.

점수는 **기록한 항목만** 본다. 냉각수를 한 번도 기록하지 않은 사람을 벌주면 점수가 차에
대한 판단이 아니라 카탈로그에 대한 판단이 되고, 모든 신규 사용자가 0점으로 시작한다.

배지는 앱 사용이 아니라 **차와 습관**에 대한 것이다. "7일 연속 실행"은 엉뚱한 것을
보상한다. 잠긴 배지도 보여 준다 — 보이지 않는 목표는 목표가 아니다.

### Android 검증은 Firebase App Distribution

개발 머신에서 Android 에뮬레이터를 돌리지 않는다. 로컬 런타임 검증은 iOS Simulator에서
하고, Android는 빌드가 통과하는지까지만 로컬/CI에서 확인한 뒤 Firebase App Distribution
으로 배포해 실기기에서 확인한다.

Firebase 프로젝트 `sycho-app-507317` 과 서비스 계정
`play-publisher@sycho-app-507317.iam.gserviceaccount.com` 을 다른 프로젝트와 공유한다.
서비스 계정 키는 **저장소에 복사하지 않고** 계정 공통 경로
`~/.keys/sycho-mobile/play-service-account.json` 을 `GOOGLE_APPLICATION_CREDENTIALS` 로
가리킨다. 사본을 만들면 키를 교체할 때 프로젝트를 전부 고쳐야 하고, 하나를 빠뜨리면
그 앱만 조용히 실패한다. CI 에서는 같은 키를 GitHub Secret 으로 넣는다.

App ID 는 `1:197519335220:android:f4e6c022de139930d0cf61`, 테스터 그룹은 다른 앱과 같은
`sycho-testers` 다. `tool/distribute_android.sh` 가 release APK 를 만들어 배포한다.

### 비밀 파일은 git-crypt (대칭키)

저장소가 public이므로 서명 키, Firebase 서비스 계정, `.env` 는 암호화해서 커밋한다.
`.gitignore` 로 빼는 대신 git-crypt를 쓰는 이유는, 파일이 버전 관리 안에 남아 있어야
CI가 쓸 수 있고 기기를 바꿔도 따라오기 때문이다.

GPG 대신 대칭키를 쓴다. 1인 프로젝트라 키 배포 대상이 없고, CI에는 base64로 인코딩한
키 하나를 GitHub Secret에 넣으면 끝난다. GPG 키링 관리 비용만 늘어난다.

한계: 암호문의 **파일 이름과 크기는 공개된다.** 이름에 정보를 담지 않는다.
키는 `~/.config/git-crypt/car-log.key` 에 있고 저장소에는 들어가지 않는다.
키를 잃으면 암호화된 파일은 복구 불가다.

### 마이그레이션은 실제 파일 DB 로 테스트한다

`createTable` 은 테이블을 **오늘 정의대로** 만든다. 나중 버전에서 추가한 컬럼도 포함해서.
그래서 컬럼 추가 단계는 그 테이블이 이미 있었을 때만 돌아야 한다 — 안 그러면 v1 에서
올라올 때 방금 만든 컬럼을 또 추가하려다 앱이 열리지 않는다.

실제로 이 버그가 있었다. Slice 0 빌드를 설치한 기기에서만 터지는 종류라 새 DB 로만
테스트했으면 출시 후에 알았을 것이다. 이제 옛 스키마로 **파일** DB 를 만들고 현재 코드로
여는 테스트가 있다 — 인메모리 DB 를 손으로 열면 `onUpgrade` 가 돌지 않는다.

### 앱 아이콘은 플랫폼마다 다르게 자른다

iOS 는 전달받은 원본(파란 배경 + 흰 세단)을 1024 로 줄여 그대로 쓴다. Android 적응형
아이콘은 전경 레이어의 바깥 1/3 이 잘려 나가므로 같은 이미지를 넣으면 차의 앞뒤가
사라진다. 그래서 배경은 원본에서 뽑은 단색(`#01609E`), 전경은 배경을 투명하게 지운 차
단독 이미지를 안전 영역(1024 중 620) 안에 넣은 `assets/icon/app_icon_foreground.png`
로 나눴다.

### 위치 권한을 요청하지 않는다

MVP 에 위치를 쓰는 기능이 없다. Apple 은 Location Service 가 실제 기능과 직접 관련되어야
한다고 요구하고, 쓰지 않는 권한은 심사에서 문제가 될 뿐 아니라 사용자에게도 이유 없는
요구다. 정비소 추천이 생기면 그때 요청한다.

## 미정 / 검증 필요

### Connected Car (현대·기아) 아키텍처

공식 API의 OAuth 흐름이 Client Secret을 요구하면 모바일 앱만으로는 안전하게 구현할 수
없다. PKCE / public client 지원 여부를 문서로 먼저 확인해야 한다. Backend가 필요하다는
결론이 나오면 Slice 7을 멈추고 이유를 기록한 뒤 논의한다. (핸드오프 문서 §17)

### 차량번호 기반 차량 조회

차량번호만으로 제조사/모델/연식을 조회하는 공개 API를 상용 서비스에서 쓸 수 있는지
확인 필요. VIN fallback을 전제로 설계한다.

### 백업 암호화 — 하지 않기로 했다

Export 파일은 평문 JSON 이다. 담긴 것은 차량 이름, 정비 날짜, 주행거리, 비용이고
자격증명은 들어가지 않는다. 암호를 걸면 사용자가 비밀번호를 하나 더 기억해야 하고,
잊으면 백업이 벽돌이 된다 — 백업의 목적과 정면으로 부딪힌다.

파일을 어디에 둘지는 사용자가 정한다. 더 강한 보호가 필요하면 암호화된 저장소에 넣으면
된다. 민감도가 올라가는 기능(예: 위치 이력)이 생기면 다시 판단한다.
